# dw-plan

## 目的

将已批准的目标拆解为可测试规格和小型垂直任务切片构成的无环序列（DAG），并明确依赖、验证命令与回滚说明。

## 适用场景

- `dw-design` 为多步骤功能、迁移或重构完成澄清与批准后。
- 清晰的请求涉及多个模块，或需要明确任务顺序与验收标准时。

## 不适用场景

- `quick` 模式下低风险的单步修改；使用 2–4 行内联检查清单，不创建完整规格文件。
- 设计决策已经确定时，不重复开展深入需求访谈。

## 输入

- 已批准的设计摘要，或清晰明确的用户需求。
- 当前仓库代码、测试执行器及依赖边界。

## 能力要求

- 可离线使用本地 `.dev-workflow/tasks/<task-id>/` Markdown 文件；只读状态下可直接在回复中输出。
- 不依赖 GitHub Issues、Linear、Jira 等外部任务系统；只有明确配置并获得授权时才同步。

## 执行步骤

1. **确认准备就绪**：核实目标和关键决策已经明确。重大歧义仍存在时，返回 `dw-design` 澄清一次，而不是凭空编造需求。
2. **生成 `spec.md`**（在可写工作区的 `standard` 或 `rigorous` 模式）：包括问题、包含范围、排除范围、决策、接口或契约、验收标准、验证计划与回滚方案。
3. **按垂直切片拆分任务**：
   - 优先顺序：契约或 Schema → 最小可运行切片 → 安全与边界验证 → 集成。
   - 每个切片都必须定义 `id`、`title`、`blocked_by`（依赖 ID）、`files`、`acceptance`、`commands`（真实验证命令）及 `rollback`。
4. **检查 DAG 无环性和共享状态安全性**：
   - 确认 `blocked_by` 不形成环。
   - 修改同一文件、锁文件、Schema 或共享测试 Fixture 的切片必须通过 `blocked_by` 串行执行，不得并行。
5. **确定下一批可执行任务**：交接给 `dw-build` 前，仅选择全部 `blocked_by` 依赖已经满足的切片。

## 输出

- `quick`：2–5 行内联执行计划及准确的检查命令。
- `standard`/`rigorous`：`spec.md` 和任务切片定义（`steps/` 或任务列表），包含明确的 `blocked_by` DAG、验收检查与回滚说明。

## 失败处理与降级策略

- 项目没有测试执行器时，应指定真实且确定性的验证步骤（类型检查、构建、CLI 冒烟脚本或手工检查清单），不得编造 `npm test`。
- 离线或未经授权时，绝不能编造外部任务系统的 Issue 或 Issue ID。

## 授权

- 向可写工作区的 `.dev-workflow/tasks/` 写入 `spec.md` 或任务切片，需要 `LOCAL_EDIT` 授权；否则只能以只读方式内联展示计划。
- 规划阶段本身不授权编辑应用代码，除非用户此前已经批准实现。

## 验证

- 每个任务都必须包含非空的 `acceptance`、`commands` 和 `rollback`。
- 确认 `blocked_by` 无环，并对共享文件和 Fixture 施加串行约束。
- 确认没有写入虚构的外部 Issue URL 或不存在的命令。
