# dw-build

## 目的

以真实测试或构建执行证据支持小范围、已验证且严格符合任务边界的代码变更，同时保护已有未提交内容和授权边界。

## 适用场景

- 经 `dw-start`、`dw-plan` 或 `dw-design` 进入已授权的 `feature`、`refactor` 或 `bug-fix` 实现阶段。
- 范围明确且获得授权的 `quick` 修改。

## 不适用场景

- 用户只要求只读分析、代码审查或设计评估。
- `rigorous` 或高影响架构变更尚未得到设计批准。
- 提交、推送、打开 PR 或发布，应使用 `dw-ship`。

## 输入

- 用户已授权的实现范围（`LOCAL_EDIT`）。
- 规格和任务切片（`spec.md`、`steps/`），或 `quick` 模式的简短内联计划。
- 当前 `git status`、基线 HEAD SHA、可用工具和测试执行器。

## 能力要求

- **保护有改动的工作区**：先检查未提交修改；不得丢弃、stash、执行 `git clean` 或 `git checkout --` 破坏用户工作。
- **测试与 TDD 适配**：
  - 在 `rigorous` 模式或高风险、可自动测试的代码中，如果有测试执行器，执行 Red → Green → Refactor，并记录失败和通过两次运行。
  - 没有自动测试框架时，运行最强的确定性替代验证（构建、Lint、类型检查、脚本冒烟测试），明确标记 `TDD: not applicable (no test framework)`，不得宣称 TDD 已通过。
- **并行执行**：
  - 默认由单 Agent 逐切片串行执行。
  - 只有宿主确实提供子 Agent 或 Worktree 工具，而且任务涉及的文件与共享状态严格不重叠时，才可并行委派。单 Agent 执行不得伪称使用了子 Agent。

## 执行步骤

1. **检查工作区**：编辑前执行 `git status` 并读取目标文件。
2. **选择下一个未阻塞的切片**：多步骤计划中，确认所有 `blocked_by` 依赖都具有已完成的证据。
3. **最小化实现**：只编辑当前切片涉及的内容，复用项目现有辅助函数，并保留无关的注释和行为。
4. **最终编辑后验证**：执行切片的针对性检查和更广泛的相关检查，记录准确命令、退出码和观察到的输出；未执行的检查必须标记 `not_run`。
5. **更新本地进度**：如使用 `.dev-workflow/tasks/<task-id>/`，以原子方式更新 `worklog.md` 和 `run-state.json`。
6. **在权限边界停止**：必要时交接给 `dw-review`，否则报告实现完成；不得自动运行 `dw-ship`。

## 输出

- 修改或创建文件的准确列表。
- 每个切片的验收标准状态。
- 最终编辑后执行的确切验证命令、退出码及简要结果；未运行或跳过的检查明确标记 `not_run`。
- 更新后的 Git 工作区状态（`git status` 摘要）。

## 失败处理与降级策略

- 如果验证因变更前已有的、不相关仓库问题而失败，需区分基线失败与本次引入的失败，并准确报告二者。
- 依赖、权限或需求歧义造成阻塞时，停止编辑，保持工作区有效状态并报告 `blocked`。

## 授权

- 必须获得用户在相应任务范围内的 `LOCAL_EDIT` 权限。
- 不得自行升级为 `LOCAL_COMMIT`、`REMOTE_WRITE` 或 `DESTRUCTIVE` 权限。

## 验证

- 每一项宣称通过的检查，都必须在**最后一次文件编辑之后**执行，且退出码为 `0`。
- 确认没有撤销或覆盖任何无关的用户未提交修改。
