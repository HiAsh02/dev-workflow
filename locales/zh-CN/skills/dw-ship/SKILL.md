# dw-ship

## 目的

对提交、推送、合并、发布或删除分别执行明确的授权检查、预检查和操作后远程核验，防止意外操作。

## 适用场景

- 用户明确要求提交变更、推送分支、创建或合并 PR、创建发布标签、发布包或删除分支/资源。
- 在申请发布授权之前，准备一次只读的交付前检查清单。

## 不适用场景

- `dw-build` 或 `dw-review` 完成后，未经明确交付请求不得自动调用。
- 不得从“代码看起来没问题”“Review 通过”或之前的本地编辑批准中推断远程发布权限。

## 输入

- 用户明确的交付指令，包括允许的操作（`commit`、`push`、`pr`、`merge`、`release`、`deploy`、`delete`）及目标仓库/分支。
- 当前 `git status`、HEAD SHA、远端 URL（`git remote -v`）和最新验证结果。

## 能力要求

- 在可用且获授权时通过 `git` 或宿主 VCS CLI（例如 `gh`）操作。
- 若缺少网络、凭据或 CLI 工具，应准备交付前清单并安全阻止执行，不得模拟远端成功。

## 执行步骤

1. **拆分所需权限**：
   - 分别评估 `LOCAL_COMMIT`、`REMOTE_WRITE`（`push`、`pr`、`merge`、`release`、`deploy`）和 `DESTRUCTIVE`（`delete`、强制推送、历史重写）。
   - 确认用户当前请求明确授权了每一项将执行的操作。
2. **交付前检查**：
   - 检查 `git status --short --branch`、`git remote -v`、`git rev-parse HEAD`。
   - 确认未跟踪的机密（`.env`、令牌、密钥）或非预期脏文件不会被暂存/推送。
   - 确认所有必需的验证（`validate`、测试、构建）均在最后一次编辑后通过，且没有尚未关闭的 `critical`/`major` 审查问题。
   - 核实目标仓库和分支与用户意图一致，不得猜测目标分支或仓库可见性。
3. **缺少授权时停止**：如任何请求或暗示的操作未得到明确的当前授权，执行前必须停止，并提供交付前检查清单（待执行操作、确切目标仓库/分支和回滚计划）。
4. **严格执行获授权步骤**：仅按安全顺序执行已批准的操作，例如只暂存特定文件，再提交、推送到已核实的分支。
5. **核验实际远程结果**：直接从工具结果读取提交 SHA、远端引用、PR URL 或发布状态后才报告成功。

## 输出

- 授权核查摘要：已授权与未授权的操作。
- 交付前检查证据：`git status`、已运行检查、目标仓库及分支。
- 已执行步骤：确切命令、提交 SHA、远端引用/PR/发布 URL，以及回滚命令。
- 未授权或受阻步骤：可执行的交付前检查清单，且不产生修改。

## 失败处理与降级策略

- 因授权、网络、分支保护或目标不符导致推送/PR 失败时，报告准确失败原因，保持本地状态干净且可恢复。
- 未单独取得 `DESTRUCTIVE` 明确授权时，绝不能强制推送（`--force`）或删除分支。

## 授权

- `LOCAL_COMMIT`、`REMOTE_WRITE` 和 `DESTRUCTIVE` 是三个不同的权限级别。
- 任务账本（`.dev-workflow/tasks/*/run-state.json`）及通过的审查**绝不**授权 `dw-ship`。

## 验证

- 操作后检查 `git status` 和远端状态，例如 `git ls-remote`、`gh pr view` 或 `gh repo view`。
- 确认没有发生未经授权的远端、分支、标签或公开可见性变化。
