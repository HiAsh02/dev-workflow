# dw-design

## 目的

在实现前消除设计歧义并明确权衡，使高影响、不可逆或跨模块工作以经过批准且不存在冲突的规格为起点。

## 适用场景

- 产品或技术需求存在尚未解决的重要歧义。
- 公共接口、持久化格式、安全边界或系统架构将发生变化。
- 用户明确要求评估或提出设计方案。

## 不适用场景

- 已确定所有约束的明确、低风险本地编辑（`quick` 模式）。
- 用户在当前对话已批准完整设计时，不要重复询问；转至 `dw-plan` 或 `dw-build`。
- 不涉及架构变更的纯缺陷诊断，应先使用 `dw-debug`。

## 输入

- 用户目标、约束及已声明偏好，不得重复询问已决事项。
- 现有仓库文件：`README.md`、`AGENTS.md`、相关源码模块、已有 ADR，以及存在时的领域术语表。

## 能力要求

- 支持通过只读仓库搜索和文件读取开展设计工作。
- 仅当工作区可写、任务范围确有必要且符合 `standard`/`rigorous` 要求时，才选择性生成设计摘要、ADR 或术语表更新。

## 执行步骤

1. **先读取已有上下文**：提问前检查代码模式、现有接口、ADR 和术语。
2. **优先复用而非发明**：优先采用项目已有的框架、辅助方法和约定，不无故增加抽象或依赖。
3. **只澄清真实阻塞点**：只有重大产品决策、安全权衡或冲突约束无法从代码库确定时，才提出聚焦的问题。
4. **比较方案**：说明推荐方案及被排除的备选方案，列出明确的非目标、受影响的不变量、风险和高层验证策略。
5. **批准关口**：对于 `rigorous` 任务以及不可逆、公共 API 或安全相关变更，开始编辑代码前必须暂停并请求用户批准设计摘要。

## 输出

一份设计摘要（中小任务可直接在回复中呈现；大型任务获得授权后可保存至 `.dev-workflow/tasks/<task-id>/` 或 `docs/`），至少包含：

- 目标、范围与非目标。
- 关键约束及既有惯例。
- 推荐设计与已考虑的替代方案。
- 风险、安全或迁移影响及验收策略。
- 需要用户批准的开放问题（如有）。

复杂的多术语业务领域或架构转向还应补充简洁的 ADR 或术语表条目。

## 失败处理与降级策略

- 经过一轮澄清后需求仍然矛盾，应明确列出冲突约束并暂停，不得为关键行为擅自设定默认值。
- 用户只要求探索设计时，不得编写猜测性的原型代码。

## 授权

- 默认严格**只读（READ-ONLY）**，直到用户批准编写设计文档或开始实现。
- 不得将设计探索解释为修改应用代码、提交或推送的权限。

## 验证

- 核对设计摘要中引用的文件路径、符号和既有约束确实来自实际观察。
- 确认没有忽略或违反已经确定的用户约束。
- 确认高影响实现没有在明确批准之前开始。
