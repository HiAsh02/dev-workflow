# dw-review

## 目的

通过可复现证据，从规格需求（`Spec`）与工程、安全标准（`Standards`）两个维度验证已完成的变更。

## 适用场景

- `dw-build` 完成切片或功能后。
- 用户要求审查分支、PR、提交范围或未提交差异时。

## 不适用场景

- 从零开展开放式架构设计，应使用 `dw-design`。
- 推送、合并或发布变更，应使用 `dw-ship`。

## 输入

- 固定比较基线（提交区间、分支合并基点、PR 差异或工作区差异）。
- 有关规格、验收标准、`AGENTS.md`，以及存在时的仓库规范。
- 安全的只读测试、Lint 或构建命令。

## 能力要求

- 默认严格**只读（READ-ONLY）**。
- 可由单 Agent 完成两轮明确审查（先 `Spec` 后 `Standards`）；只有宿主确实具备子 Agent 工具时，高风险差异才可委派对抗式检查。若只有一个 Agent 会话审查，不得伪称存在“独立审查者”。

## 执行步骤

1. **固定审查基线**：确定准确的基线提交或分支，检查完整差异（`git diff`、`git status`）。
2. **轴一：规格符合性（Spec）**：
   - 将实现行为与既定目标、`spec.md` 和验收标准逐项比较。
   - 指出缺失需求、未经批准的范围扩张；若不存在正式规格，必须明确标记。
3. **轴二：标准和风险（Standards）**：
   - 检查正确性、边界条件、错误处理、安全/注入风险、路径及权限安全、向后兼容性和测试质量。
   - 对高风险差异，追踪具体失败或攻击路径，提供 `file:line` 和机制。
4. **实证核查**：条件允许时自行运行安全、只读的验证（`validate`、测试、构建），不直接相信以前的文字总结。
5. **区分事实与假设**：
   - 仅报告有直接观察到的代码或输出依据的问题。
   - 未执行的运行时场景必须标记 `unverified` 或 `not_run`。
6. **严重度分级**：使用 `critical`、`major`、`minor`、`info`；未解决的 `critical` 或 `major` 阻止交付就绪（`dw-ship`）。

## 输出

结构化审查报告，包含：

- 审查范围及差异基线（`base..head` 或工作区）。
- Spec 轴评估。
- Standards 轴评估。
- 按严重度排序的问题（`severity`、`file:line`、`evidence`、`impact`、`suggested fix`、`blocking: yes|no`）。
- 已执行的验证命令、退出码和未验证缺口。
- 发布关口结论：`PASS`、`CHANGES_REQUESTED` 或 `BLOCKED`。

## 失败处理与降级策略

- 环境无法执行测试时，记录 `not_run` 和具体障碍，不得声称检查通过。
- 差异为空或比较基线不清楚时，在得出结论前询问目标范围。

## 授权

- 严格**只读（READ-ONLY）**：代码审查绝不自动授权修复、提交、推送或合并。
- 只有收到用户明确的修复授权后，才能编辑代码。

## 验证

- 确认所有引用的 `file:line` 和命令输出均在当前会话中实际观察到。
- 确认只读审查期间没有修改任何文件。
